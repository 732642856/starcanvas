## 5. 最近完成：Issue #5 多项目 Canvas 隔离 e2e

### 5.1 背景

此前 v0.1.0-rc.2 修复了多项目 canvas 共享同一个持久化 key 的风险。核心函数在：

```text
apps/web/src/app/canvas/hooks/useCanvasPersistence.ts
```

关键逻辑：

```ts
DEFAULT_STORAGE_KEY = "startrails_canvas"
getCanvasStorageKey(projectId?)
```

行为：

- 无 `projectId`：`startrails_canvas`
- 有 `projectId`：`startrails_canvas_p:${encodeURIComponent(projectId)}`

### 5.2 新增测试文件

```text
apps/web/e2e/project-canvas-isolation.spec.ts
```

覆盖 8 个场景：

1. 默认 canvas 内容不会出现在 project-scoped canvas
2. 特殊字符 projectId 内容不会出现在默认 canvas
3. Project A canvas 不会出现在 Project B
4. Project B 初始为空，不继承 Project A
5. 返回 Project A 能恢复自己的 canvas 状态
6. Project A / B round-trip 后各自状态独立
7. 两个特殊字符 projectId 不发生 key collision
8. 无 projectId 时回退默认 canvas，保持向后兼容

### 5.3 测试策略说明

最终采用：**legacy localStorage payload 注入 + 页面行为验证**。

原因：

- 通过 UI 创建节点的 helper 不稳定，Playwright 中容易停留在 onboarding 空画布状态。
- 直接写 IndexedDB / supermemory 容易被当前挂载页的空 canvas 保存逻辑覆盖。
- `useCanvasPersistence` 本身支持 `supermemory.get() ?? localStorage fallback`，所以 localStorage 注入可以稳定验证 storage key 隔离、恢复和默认 key 兼容行为。
- `hasMarkerText` 同时检查 `document.body.textContent` 与 `input/textarea.value`，因为 ContentNode 的正文常渲染在 textarea 中，不一定出现在 `textContent`。
- 使用 `expect.poll` 等待异步恢复，避免刚看到 React Flow shell 就立即断言导致假失败。

## 6. 当前关键约束：务必遵守

1. **不要更换包管理器**：继续使用 pnpm。
2. **优先改 `apps/web/`**：除非明确需要，暂不动 `apps/api`、`packages/providers`、`packages/billing`。
3. **不要大范围重构**：当前阶段以稳定化和可验证优化为主。
4. **React Flow 节点更新要防 stale read**：`setNodes` 必须优先用函数式更新；更新后立刻读节点时要同步 `nodesRef.current`。
5. **direct-only 分镜生图保护**：多镜头生图只能发起一次最终 `generate-image` API call，严禁 fallback 到逐镜头调用，避免浪费额度。
6. **测试框架优先 node:test**：不要为了小测试新增 Vitest 依赖；项目虽有 `test:vitest` 脚本，但既有单测主线仍以 node:test 为主。
7. **Playwright 端口**：e2e 默认端口 `3107`，`playwright.config.ts` 中 `reuseExistingServer: false`，如测试异常先检查端口占用。
8. **GitHub CLI 未必可用**：此前 `gh` 不在 PATH 时使用 `git credential fill` + `curl` 调 GitHub API。若用 `curl`，记得必要时 `unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy`。
